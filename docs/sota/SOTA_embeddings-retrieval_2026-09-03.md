# State of the art, embedding + retrieval stack for a one-box "second brain" (as of 2026-09-03)

Target: ~300 markdown design docs, ~20k chat-transcript messages, later a 172M-token corpus. One Windows box, RTX 4070 Ti SUPER 16 GB (672 GB/s), llama.cpp local, paid APIs optional.
Method: 46 web searches + ~75 primary-source fetches (arXiv, HF model cards, vendor docs). The HF MTEB/RTEB leaderboard pages are SPAs and could not be fetched; every score below is the self-reported number on the model card or paper, with its date. Anything I could not confirm in a primary source is tagged **UNVERIFIED**. Box-specific latency/throughput numbers are **computed estimates** unless a source is cited.

## 0. Corpus math (drives every recommendation)

- 172M tokens at ~400-token chunks with ~15% overlap ≈ 0.5M chunks (≈0.39M at 512 tokens). At 1024-d: fp16 = 1.0 GB, int8 = 0.5 GB, binary = 64 MB. At 4096-d (Qwen3-8B / Nemotron-8B native): fp16 = 4 GB.
- Exact (brute-force) scan of 0.5M × 1024 int8 on the GPU is bandwidth-bound: 0.5 GB / 672 GB/s ≈ 0.8 ms; fp16 ≈ 1.5 ms; CPU int8 with AVX2/AVX-512 ≈ 10–20 ms (estimate). No ANN index is needed below ~10^7 vectors on this box; exactness removes an entire class of recall bugs.
- Multi-vector (ColBERT) over the same corpus: 172M token vectors × 128-d int8 = 22 GB; × 48-d int8 = 8.3 GB; Vespa-style 16 B/token compression ≈ 2.75 GB. That is why late interaction below is used as a *re-scorer*, not a first-stage index.
- Embedding throughput on this GPU (**UNVERIFIED estimates**, measure with `llama-bench`/`llama-embedding`): Qwen3-Embedding-0.6B Q8_0 ≈ 15–30k tok/s batched → ~200M tokens (with overlap) in 2–4 h; 4B Q8_0 ≈ 5–8k tok/s → 7–11 h; 8B Q4_K_M ≈ 2.5–4k tok/s → 14–22 h. Full re-embeds are therefore an overnight job, not a project.
- API cost for one full pass (~200M tokens): voyage-4-lite $4, voyage-4 $12, voyage-4-large $24 (and the first 200M tokens per account are free) — https://docs.voyageai.com/docs/pricing (2026-08-26); gemini-embedding-001 $30 ($15 batch), gemini-embedding-2 text $40 ($20 batch) — https://ai.google.dev/gemini-api/docs/pricing (fetched 2026-09-03).

### A2. Retrieval architecture: hybrid first stage, convex-combination fusion, exact scan

1. Two first-stage retrievers: dense (A1) + lexical BM25 over the *same* chunks, with contextual headers prepended to both (A4).
2. Fuse with **convex combination of min-max-normalized scores, α≈0.5**, not RRF. Evidence: Bruch et al. (TOIS 2023, arXiv 2022-10-21) — CC beats RRF in- and out-of-domain, RRF is sensitive to k, CC needs only a handful of tuning examples https://arxiv.org/abs/2210.11934; April 2026 text-and-table benchmark: BM25 R@5 0.644, dense (text-embedding-3-large) 0.587, RRF(k=60) 0.695, CC(α=0.5) 0.726, contextual-hybrid 0.717, hybrid+rerank 0.816 (+12.1 pp from the reranker alone) https://arxiv.org/html/2604.01733v1.
3. Learned sparse (SPLADE-v3) is optional: it was the sparse leg of the 3rd-place SemEval-2026 Task 8 multi-turn RAG system (0.5453 nDCG@5 vs 0.4795 baseline; SPLADE-v3 + dense + RRF + cross-encoder) https://arxiv.org/abs/2606.28352, but costs 45–100 ms/query for an encoder pass (Prem AI, secondary) and SPLADE-v3's license is CC BY-NC-SA (**UNVERIFIED** this session). For a personal corpus, contextual BM25 captures most of the lexical gain at zero GPU cost.
4. Store vectors int8 (or fp16) in sqlite-vec / usearch / faiss `IndexFlat` (GPU via cuVS) and scan exactly; keep binary copies only if you later exceed ~5M vectors.

### A4. Chunking recipes

**Markdown design docs.** Structure-aware chunking on heading boundaries, target 256–512 tokens, split oversize sections recursively, prepend a contextual header (doc title › heading path › one-sentence LLM-written context). Evidence: 36-strategy study (2026-03-07) — paragraph-group chunking nDCG@5 0.459 vs fixed-character 0.244; structure-aware/adaptive "moderate" sizes win; larger embedders raise the ceiling but stay sensitive to bad segmentation https://arxiv.org/html/2603.06976. Anthropic contextual retrieval (2024-09-19): contextual embeddings cut top-20 failures 35% (5.7→3.7%), + contextual BM25 49% (→2.9%), + rerank 67% (→1.9%); chunks of "a few hundred tokens", pass top-20 to the model; $1.02 per M doc tokens with prompt caching at 2024 prices https://www.anthropic.com/news/contextual-retrieval. Semantic chunking is not worth it: Vectara/NAACL 2025 (arXiv 2024-10-16) https://arxiv.org/abs/2410.13070; the widely cited Feb-2026 "7 strategies, 50 papers: recursive-512 69%, fixed-512 67%, semantic 54% (43-token fragments)" comes from a Prem AI summary (2026-03-17) https://www.premai.io/blog/rag-chunking-strategies-the-2026-benchmark-guide/ — the original (runvecta.com) did not resolve, so **UNVERIFIED**. Adaptive per-document chunker selection lifted answer correctness 62–64% → 72% (2026-03-26) https://arxiv.org/abs/2603.25333 — worth it only if doc types are heterogeneous.

**Late chunking** (Jina, 2024-09-07): +1.5–1.9 pts absolute nDCG@10 on BEIR, largest for *small* chunks, needs a long-context encoder with **mean pooling** https://arxiv.org/html/2409.04701. Qwen3-Embedding and jina-v5 use last-token pooling, so late chunking does not apply to them (trap C4); nomic-embed-text-v2-moe or EmbeddingGemma are the mean-pooled options. The 2025-04-28 comparison found contextual retrieval more coherent but costlier, late chunking cheaper but less complete https://arxiv.org/abs/2504.19754. Recommendation: contextual headers (works with any embedder) over late chunking.

**Chat transcripts.** Do not embed single messages only. Index three granularities: (1) turn-pairs/segments of ~5–15 messages with speaker labels and a session header; (2) per-session LLM summary; (3) extracted facts/entities. Evidence: LMEB (2026-03-13, rev 2026-08-03) — dialogue tasks at turn/round/session granularity; MTEB rank *anti-correlates* with LMEB-Dialogue (Pearson −0.496) and is orthogonal overall (−0.115); top models bge-multilingual-gemma2 61.41, NV-Embed-v2 60.25, KaLM-Gemma3-12B 60.10, Qwen3-8B 55.94 https://arxiv.org/html/2603.12572. LongMemEval-V2 (2026-05-12): query→slice RAG 42.8%, +notes pool 51.0%, structured runbooks 74.9%; removing the raw-slice pool costs 28.6 pts on static questions — multi-level pools are essential https://arxiv.org/html/2605.12493v1. H-RAG parent-child (child sentences, parent = full turn) 0.4271 nDCG@5 at SemEval-2026 Task 8 https://arxiv.org/abs/2605.00631; SGMem sentence graphs across turn/round/session (2025-09-25) https://arxiv.org/abs/2509.21212. Mem0's 2026 stack fuses semantic + BM25 + entity signals https://mem0.ai/blog/ai-memory-benchmarks-in-2026 (2026-09-02).

### A5. Index + quantization plan (numbers)

- **Exact scan first.** sqlite-vec v0.1.9 (2026-03-31) is brute-force with int8/binary columns; v0.1.10-alpha.4 (2026-05-18) adds rescore/IVF/DiskANN https://github.com/asg017/sqlite-vec/releases. usearch HNSW: i8 274,653 QPS at 98.9% recall@1 vs f32 131,654 QPS at 99.3% (64-core Graviton 3; "8-bit has almost no quantization loss") https://github.com/unum-cloud/usearch/blob/main/BENCHMARKS.md. faiss-gpu now wraps cuVS for `GpuIndexFlat`/IVF https://github.com/facebookresearch/faiss/wiki/GPU-Faiss-with-cuVS; NVIDIA's own guidance: IVF-Flat when the index fits GPU memory, CAGRA for small-batch ANN, brute force when you want exact https://developer.nvidia.com/blog/accelerating-vector-search-fine-tuning-gpu-index-algorithms/ (2023-09-11). The May-2026 relational-engine study warns GPU wins only when data movement is avoided https://arxiv.org/abs/2605.15957 — so keep the matrix resident in VRAM or stay on CPU.
- **Quantization retention** (HF blog 2024-03): int8 + rescore ≈ 99% of fp32 nDCG@10, 4× smaller, 3–4.8× faster; binary ≈ 92.5% raw, ≈ 96% with 4× rescoring, 32× smaller, 15–46× faster https://huggingface.co/blog/embedding-quantization. Elastic BBQ: >90% recall at 3× oversampling on 1M × 1024-d, 138M vectors 535 GB → 19 GB, 18 ms/query with 50-doc rerank (2024-11) https://www.elastic.co/search-labs/blog/better-binary-quantization-lucene-elasticsearch. RaBitQ (SIGMOD 2024) gives the theoretical error bound PQ lacks https://arxiv.org/abs/2405.12497; ">95% recall" with ≤100-candidate rescoring https://www.elastic.co/search-labs/blog/rabitq-explainer-101; IVF-RaBitQ ships in LanceDB ("multi-bit RaBitQ 96% recall without refine", undated) https://www.lancedb.com/blog/feature-rabitq-quantization, Milvus, cuVS, Weaviate.
- **MRL truncation**: Mixedbread 512-d binary keeps 90.76% (64 B/vector), 256-d 79.5%, 128-d 60.3% (2024-04-12) https://www.mixedbread.com/blog/binary-mrl; jina-v5 "declines substantially below 256" https://arxiv.org/html/2602.15547v2; EmbeddingGemma 768→256 loses only 1.5 MMTEB pts https://huggingface.co/google/embeddinggemma-300m. Rule: keep ≥ 1024-d int8 for the primary index at this scale (0.5 GB); never binary-only without rescoring.
- **Multi-vector** if you add a ColBERT rescorer: MUVERA fixed-dimensional encodings give single-vector search with 2–5× fewer candidates and "10% better recall at 90% lower latency" than prior multi-vector engines (rev 2026-06-08) https://arxiv.org/abs/2405.19504; WARP is 3× faster than PLAID and 41× faster than XTR's reference (SIGIR 2025) https://arxiv.org/abs/2501.17788; GEM graph index claims up to 16× over SOTA (2026-03-20) https://arxiv.org/abs/2603.20336.

### A6. Late interaction: use as a rescorer on long documents

- Where it wins: long documents and out-of-domain. GTE-ModernColBERT-v1 (0.1B, Apache-2.0) LongEmbed 88.39 vs voyage-multilingual-2 79.17, BEIR 54.67 https://huggingface.co/lightonai/GTE-ModernColBERT-v1; mxbai-edge-colbert-v0-17m (17M, 48-d tokens, 32k ctx) LongEmbed 0.847 at 32k, BEIR 0.490 vs ColBERTv2 0.488 https://huggingface.co/mixedbread-ai/mxbai-edge-colbert-v0-17m (Oct 2025); Mixedbread's "17M ColBERT beats 8B embedders on LongEmbed" (2026-01-21) https://www.mixedbread.com/blog/multimodal-late-interaction-billion-scale; Vespa MLDR: context-level MaxSim ≈0.73 nDCG@10 vs E5-Mistral-7B ≈0.48 (2024-03-01) https://blog.vespa.ai/announcing-long-context-colbert-in-vespa/; Jina-ColBERT-v2 BEIR 53.1 vs ColBERTv2 49.6, 64-d tokens lose only 1.59% https://arxiv.org/html/2408.16672. The LIR@ECIR-2026 workshop frames the field as "strong generalisation, particularly out-of-domain" with efficiency/usability as open problems https://arxiv.org/abs/2511.00444.
- Where it loses: long *queries*. SIGIR-2026 reproduction: ColBERT-v2/ConstBERT drop 86–97% on long narrative queries (TREC ToT 2025) because uniform MaxSim token weighting "cannot distinguish signal from filler", plateauing at ~20 query words https://arxiv.org/abs/2604.09982. Chat-style, paragraph-length queries must be rewritten/condensed before a ColBERT stage.
- Vision docs: Nemotron ColEmbed V2 8B is #1 on ViDoRe V3 (63.42 nDCG@10, 2026-02-03) https://arxiv.org/abs/2602.03992; ColQwen2.5 remains the practical open default https://github.com/illuin-tech/colpali. Not needed for markdown + chat.
- No llama.cpp path for ColBERT-style models was verified (`--pooling none` returns per-token vectors, but ModernBERT-arch support is **UNVERIFIED**); run PyLate/ONNX on the GPU.

### A7. Model swap / drift policy

- Budget for full re-embeds (A0: overnight locally, $0–24 via Voyage). Alias-swap indexes (build new index in parallel, atomically repoint).
- If you cannot re-embed: Drift-Adapter (2025-09-27) maps new-model queries into the legacy space via orthogonal Procrustes / low-rank affine / small MLP, recovering 95–99% Recall@10/MRR with <10 µs overhead from a small paired sample https://arxiv.org/abs/2509.23471; Procrustes bounds (2025-10-15) give the theory https://arxiv.org/abs/2510.13406; Query Drift Compensation (2025-05-27) projects new queries onto old corpus embeddings https://arxiv.org/abs/2506.00037. Voyage 4's shared space is the only vendor-native version of this https://blog.voyageai.com/2026/01/15/voyage-4/.
- Asymmetric prompting is now universal and model-specific (table A1); ERA (2026-08-26) shows a strong query embedder + light document embedder with a learned adapter gains +8.2 nDCG symmetric / >12 asymmetric on MAIR with <100 labels https://arxiv.org/html/2604.03403 — the same idea Voyage sells. Persist the exact instruction string and model hash with every index; a changed instruction string is a silent model swap.

### A8. Expected recall / latency on this box (estimates unless cited)

- Query path: embed query (0.6B Q8) 10–20 ms → int8 exact scan 0.5M×1024 <2 ms GPU / 10–20 ms CPU → BM25 (FTS5/tantivy) 5–20 ms → CC fusion <1 ms → Qwen3-Reranker-0.6B over 50 docs 0.3–0.6 s (4B: 1.5–3 s). End-to-end ≈ 0.5–3.5 s.
- Quality ordering to expect (from the closest published analogue, 2026-04 finance docs): dense-only R@5 ≈ 0.59, BM25 ≈ 0.64, CC hybrid ≈ 0.73, hybrid+rerank ≈ 0.82 https://arxiv.org/html/2604.01733v1. Absolute numbers will differ; the ordering is what to verify locally.
- VRAM budget: Qwen3-Embedding-4B Q8 (~4.3 GB) + Qwen3-Reranker-4B Q8 (~4.3 GB) + 0.5 GB int8 matrix + KV/scratch ≈ 10 GB; leaves ~6 GB for a small chat model.

## C. Traps and unverified claims

1. **jina-v5 in llama.cpp truncates at ~512 tokens** (issue #19865, closed-not-planned 2026-02-24). Test with a 1,500-token input before adopting; otherwise run it via sentence-transformers/vLLM. https://github.com/ggml-org/llama.cpp/issues/19865
2. **Qwen3-Reranker community GGUFs return ~1e-23 scores** (missing `cls.output.weight`, no `pooling_type=RANK`). Convert from the HF repo with current `convert_hf_to_gguf.py`; sanity-check that a relevant/irrelevant pair separates. Issue #16407 remains open. https://gist.github.com/VooDisss/42bce4eb5c76d3c325633886c5e348ee
3. **Instruction/prefix mismatch = silent model swap.** Qwen3 (query-only `Instruct:`), jina-v5 (`Query:`/`Document:` mandatory), EmbeddingGemma (`task: … | query:` vs `title: none | text:`), Nemotron (`query: `/`passage: `), voyage-4-nano (long English prompts), Gemini 2 (instruction in prompt, no task_type). Store the exact string with the index.
4. **Late chunking needs mean pooling.** Qwen3-Embedding and jina-v5 are last-token pooled, so "late chunking" with them is undefined; use contextual headers instead. https://arxiv.org/html/2409.04701
5. **MTEB rank does not predict chat-memory retrieval** (LMEB ρ −0.115 overall, −0.496 on dialogue). Evaluate transcript retrieval on your own transcripts. https://arxiv.org/html/2603.12572
6. **Rerankers can hurt on memory retrieval** (−6.9 Hit@1 on LoCoMo/LongMemEval with a cross-encoder). Gate by source. https://arxiv.org/abs/2606.04194
7. **Late interaction collapses on long queries** (−86–97% on narrative queries). Condense queries to ≤~20 content words before a ColBERT stage. https://arxiv.org/abs/2604.09982
8. **BEIR numbers across reranker papers are not comparable** (Jina's table gives mxbai-large-v2 61.44; Mixedbread's own blog gives 57.49 on a different subset). Compare only within one paper's table.
9. **Binary-only indexes lose 7–8% nDCG without rescoring**; MRL below 256-d loses a lot more. Always rescore with int8/fp16. https://huggingface.co/blog/embedding-quantization
10. **The llama.cpp `n_ubatch ≥ n_tokens` rule**: start the server with `-ub` ≥ your longest chunk or long chunks error/truncate. https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md
11. **`/v1/embeddings` normalizes, `/embedding` may not** — verify vector norms once; older Qwen card notes about manual normalization may be stale.
12. **Cohere Rerank 4 vendor claims** ("outperforms Voyage and Jina") could not be extracted from Cohere's page (HPCwire 403); only Agentset's ELO is cited. **UNVERIFIED**.
13. **"Recursive-512 69% vs semantic 54%"** (Vecta/FloTorch, Feb 2026) is cited only via Prem AI; original domain did not resolve. **UNVERIFIED**.
14. **"Octen-Embed 79.38 on RTEB"** appeared in a search snippet; no primary source identified. **UNVERIFIED**. Nemotron-3-Embed-8B's 78.5 #1 claim is NVIDIA's own (2026-07-16).
15. **"BGE-3 on a Qwen3 base"** — no primary source. **UNVERIFIED**. BGE-M3 (2024) remains BAAI's retrieval model of record.
16. **OpenAI successor to text-embedding-3** — rumour only. **UNVERIFIED**.
17. **Throughput/latency figures for this GPU** in A0/A8 are computed from bandwidth and parameter counts, not measured. Measure with `llama-bench` and a 10k-chunk sample before committing to the 172M pass.
18. **GGUF availability for Nemotron-3-Embed, KaLM-Gemma3-12B, zerank-2, GTE-ModernColBERT** — not confirmed. **UNVERIFIED**.
19. **SPLADE-v3 and jina-reranker-v3 licenses** (believed non-commercial) — not re-checked this session. **UNVERIFIED**.
20. **Third-party MTEB "2026 leaderboards"** (Presenc, CodeSOTA, Morph) report numbers inconsistent with model cards (e.g., BGE-M3 "68.2"); ignore them.

### Bottom line for this box

Qwen3-Embedding-4B (Q8, MRL→1024, int8 exact scan in VRAM) + contextual-header structure-aware chunks at 256–512 tokens + contextual BM25, fused by convex combination (α≈0.5), reranked by a self-converted Qwen3-Reranker-4B (or 0.6B) through llama-server `/v1/rerank`; a GTE-ModernColBERT rescorer only for long design docs with condensed queries; transcripts indexed at segment + session-summary + fact granularity with the reranker gated off for that source; Voyage 4 as the paid fallback because its shared space and 200M free tokens make the 172M-token pass and any later model swap nearly free.
